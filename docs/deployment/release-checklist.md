# Проверка релиза

Этот список применяется к первому запуску и каждому последующему обновлению
Куда.Крым. Команды не привязаны к конкретному хостингу: их можно использовать в
App Platform, CI/CD или на VPS.

## Перед публикацией

1. Убедиться, что выбранный коммит находится в `main`, а CI завершился успешно.
2. Создать резервную копию production-базы перед изменением её схемы.
3. Задать секреты и адреса в панели хостинга, не сохраняя их в Git:
   `DATABASE_URL`, `SITE_URL`, `WEB_ORIGIN` и при наличии `REDIS_URL`.
4. Проверить файл production-переменных локально:

   ```powershell
   npm run check:release-config
   ```

5. Собрать приложение из зафиксированного commit SHA, а не из незакоммиченных
   локальных файлов.

## Подготовка базы

При каждом релизе применяются только существующие Prisma-миграции:

```powershell
npm run database:migrate
```

Для новой пустой базы один раз применяется начальный каталог:

```powershell
npm run database:bootstrap
```

`database:bootstrap` нельзя добавлять в автоматический сценарий каждого деплоя:
повторный seed может перезаписать сведения, изменённые после публикации.

## После публикации

1. Передать адреса web и API проверочному сценарию:

   ```powershell
   $env:DEPLOYMENT_WEB_URL="https://example.ru"
   $env:DEPLOYMENT_API_URL="https://api.example.ru"
   npm run check:deployment
   ```

2. Вручную открыть главную страницу, каталоги побережья и пляжей, один прогноз и
   форму рекомендаций.
3. Проверить журналы API: в них не должно быть циклических перезапусков, ошибок
   подключения к PostgreSQL или постоянных отказов внешних источников.
4. Проверить `/robots.txt`, `/sitemap.xml` и canonical URL на фактическом домене.
5. Зафиксировать опубликованный commit SHA и время релиза.

## Откат

Если ошибка относится только к приложению, повторно развернуть предыдущий
успешный commit SHA и снова выполнить `check:deployment`.

Не откатывать каталог миграций удалением файлов и не выполнять `prisma migrate
reset` в production. Если новая схема повредила данные, остановить запись,
восстановить резервную копию и только затем развернуть совместимую версию
приложения.

## Первая публичная демонстрация

До появления коммерческой нагрузки допустимо использовать бесплатные сервисы
для web, API и PostgreSQL. Ограничения бесплатных тарифов нужно считать частью
окружения: API может засыпать, первый запрос — выполняться дольше, а база —
приостанавливаться после периода бездействия. Redis для демонстрации необязателен,
поскольку API сохраняет работоспособность без кеша.
