# Итоговый рейтинг рекомендаций

Рейтинг строится после фильтрации пляжей и усреднения прогноза внутри выбранного
временного окна. Он не подменяет отсутствующие данные нулями.

## Веса приоритетов

- спокойное море: море 65%, погодный комфорт 35%;
- комфортная погода: море 35%, погодный комфорт 65%;
- тёплая вода: море 35%, погода 25%, температура воды 40%.

Температура воды переводится в балл той же кривой, которая используется внутри
оценки морских условий.

## Уверенность

Для компонентов рассчитывается взвешенное покрытие данных, затем оно умножается
на коэффициент свежести (см. ниже). Полученная уверенность влияет на итоговый
рейтинг: сырой балл умножается на коэффициент от 0,7 до 1,0:

```text
коэффициент = 0,7 + 0,3 × уверенность / 100
```

Так высокий результат на неполных данных остаётся видимым, но не получает такое
же доверие, как полностью подтверждённый прогноз. После штрафа кандидаты
сортируются по баллу, затем по уверенности. Подбор возвращает до десяти вариантов:
три основных и остальные в раскрываемом списке.

## Время подбора и неполный результат

Подбор ограничен 20 секундами, включая ожидание каталога. Этап маршрутов
ограничен 10 секундами от начала подбора, чтобы оставить время на прогнозы.
По истечении срока новые загрузки кандидатов не запускаются, а ненужные
внешние HTTP-запросы отменяются. Уже полученные маршруты и полные прогнозы
используются для результата. Ответ содержит `meta.timedOut: true`, если
проверка прервалась по времени; интерфейс сообщает, что проверены не все пляжи.
Пустой результат при таймауте не выдаётся за отсутствие подходящих пляжей.
Если не удалось дождаться даже каталога, API возвращает 504
`RECOMMENDATIONS_TIMEOUT`. Уже отправленный запрос к БД может завершиться
позже, но не запускает дальнейшую проверку кандидатов.

OSRM получает не более четырёх одновременных запросов на процесс API,
включая отдельный расчёт маршрутов. Очередь ограничена 100 заданиями;
переполненные задания завершаются как недоступный маршрут. Лимит 8 секунд
на маршрут включает ожидание свободного слота и загрузку ответа.

Отмена одного подписчика не прерывает общий запрос, пока его ждут другие.
После ухода последнего подписчика общий HTTP-запрос отменяется. Web ожидает
API не дольше 25 секунд; закрытие соединения также прекращает подбор.

## Свежесть данных в рекомендациях

Каждый вариант передаёт `freshness`: статус и время получения данных погоды
и моря. Данные модельного сравнения в подборе не используются
(`weatherModels: null`). Интерфейс показывает даты обновления по московскому
времени и предупреждает о статусе `STALE`, включая дополнительные варианты.
Старый ответ без метаданных не считается свежим: время обновления помечается
как неизвестное.

Уверенность рассчитывается как взвешенное покрытие показателей, умноженное
на коэффициент свежести. Для возраста используется более старый из двух
источников; момент оценки общий для всех кандидатов в одном подборе.
Применяется существующая кривая свежести: до 3 часов — 100%, 6 часов — 80%,
12 часов — 55%, 24 часа — 25%, 36 часов и более — 0%;
между точками используется линейная интерполяция.
Если хотя бы один источник возвращён из устаревшего кеша, коэффициент
дополнительно ограничен 80%, даже при небольшом возрасте.

Итоговая формула: `уверенность = покрытие × свежесть / 100`;
`рейтинг = сырой балл × (0,7 + 0,3 × уверенность / 100)`.
Сами измерения и сырой балл условий не меняются. Это эвристическая оценка
качества данных, а не вероятность точности прогноза.
`generatedAt` в текущих провайдерах означает время получения ответа,
а не время выпуска метеомодели.
